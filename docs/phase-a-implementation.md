# Phase A implementation plan

**Status:** owner-authorized on 18 October 2026.

## Objective

Ship the non-holding SIZA core flow: a host creates a request, approved helpers are offered work fairly, one helper atomically accepts each slot, assignment reveals only the permitted details, the host supplies a check-in code, both parties can confirm or report, and admin can approve helpers and resolve operational queues.

## Acceptance criteria

1. Every account has one server-checked role (`host`, `helper`, or `admin`) and recorded terms/privacy consent.
2. Host requests are validated, idempotent, ownership-scoped and priced from server configuration; the client cannot set an arbitrary price or status.
3. Helper applications validate age/identity fields and documents, store private documents only in a private bucket, and remain pending until all admin checks pass.
4. Booking transitions use one table-driven state machine; illegal transitions fail.
5. Rotation ranks eligible helpers by recent completed jobs, then recency, then a deterministic random tie-break; offers are time-windowed.
6. Acceptance is an atomic conditional claim. Repeated or concurrent acceptance cannot fill a slot twice or let one helper take two slots.
7. Redacted views hide address and phone details until assignment; unassigned helpers cannot read them.
8. Check-in uses a six-digit CSPRNG code stored only as an HMAC, locks after five wrong attempts, and expires after the configured window.
9. Reports and confirmation locks are server-side and admin-visible. Declining an offer has no penalty; strikes are limited to no-show/misconduct decisions.
10. A helper's first completed job is free; later accepts are denied when subscription eligibility is not active. No card holding, payout, ledger or recurring payment code is added in Phase A.
11. Tests cover the abuse paths and the fast verification gate passes.

## Stage 3.3 atomic helper check-in

The current helper check-in path validates the submitted code in the server, then calls a counter function that moves the booking to `in_progress`, then separately writes `checked_in_at` on the assignment. A failed final write can leave those states inconsistent. Consolidate attempt, booking-state, assignment check-in, and lock-expiry reset in one service-role-only database function. Keep HMAC verification in the server; the client never receives or supplies a trusted match flag. The function must recheck the active helper role, accepted assignment, booking state, code expiry, and active lock while holding the booking row lock. Wrong attempts count atomically and the configured limit/lock duration reset after the lock window. An already checked-in helper may safely replay a correct-code request.

The legacy counter RPC is unused after this change and is removed in a forward-only migration. Store the max-attempt and lock-duration numbers in `app_config`; a newly reached lock writes a PII-free audit event. Host replacement-code issuance preserves attempts/lock and updates only while the booking remains assigned. Email notification to an admin remains in the Stage 4.2 email milestone. Local Supabase tests cover role/ownership denial, direct RPC denial, five concurrent wrong attempts, lock expiry and reset, expired codes, valid check-in atomicity, and code-replay behavior. No user-facing copy, pricing, or linked database changes are in scope.

## Stage 2.3 PostgreSQL login limiter

The owner selected a Postgres-backed login limiter; decision and threat rationale are in [ADR 010](adr/010-postgres-login-limiter.md). Login failures increment two counters atomically: the account/IP pair locks after 5 failed attempts in 15 minutes, while 20 failed attempts in an hour for one account require Turnstile on the next attempt and do not lock that account across IPs. Successful authentication clears the account and current-pair counters. Counter subjects are keyed HMAC digests, raw account identifiers and IPs are never stored, and limiter failures fail closed. The generic request limiter and login-specific counters share Postgres but use separate buckets and policies.

Forward-only migration `20261026103000_postgres_rate_limits.sql` was applied to loopback Supabase only. Local integration verifies anon denial, configured bucket limits, pair lockout, cross-IP account challenge, and counter cleanup. Unit tests verify digest privacy and fail-closed behavior. No linked Supabase write occurred and `0001_init.sql` remains immutable. Admin MFA and full session/security review remain launch blockers.

## Exact request order

`prototype switch → rate limit → bot check → input validation → authorisation → server service → database`

The central proxy and every API route/server action use the same prototype helper. The route/action still performs the remaining steps in this exact order; service-role database access is last. The pipeline contract is shared in `src/server/policies/request-pipeline.ts`, with a side-effect-free ordered core in `src/server/policies/request-pipeline-core.ts` so phase ordering and fail-closed behavior can be tested without Next.js or external providers.

For API routes, rate limiting uses the existing per-route subject convention; the admin-action limiter keys by the verified signed-in user ID when available and otherwise by IP. Identity lookup used only to select that key remains part of the rate-limit phase; role/ownership authorization remains after validation. A public bot check is an explicit route option and receives a token extracted from a cloned request body; routes without public bot exposure declare that policy explicitly. Input parsing/validation runs only after rate and bot checks. Cookie-backed API authorization includes same-origin validation before role/ownership checks. Server actions use the same prototype/rate/bot/validation/authorization/service runner; Next.js provides their origin validation, and their rate-limit subject uses request headers without resolving a role or querying domain records. Routes retain their own JSON, redirect, and form response mapping after the service result.

No database access is part of the pipeline wrapper itself. Services receive any database client only after the pipeline has completed authorization. Existing business services and database functions remain the only data mutation paths.

## Admin helper assignment transaction (Stage 2.1 prerequisite)

Admin selection remains display-only in the browser: the client submits a shortlist version and numeric indexes, and the server resolves those indexes to helper UUIDs after reloading the current shortlist. The assignment mutation must pass the prototype switch, then its abuse controls, strict input validation, and admin authorization before it calls the server service. Database work is one forward-only SQL function call, not a loop of individually committed slot claims.

The database function rechecks the actor's admin profile and membership, the booking's host profile role, booking state, remaining slots, selected helper uniqueness, profile role, approval, subscription eligibility, and service/suburb eligibility while holding the booking row lock and the selected helper/profile rows. It inserts all assignments, updates the booking state, and writes the audit event in the same transaction. Admin status changes use a sibling transaction so a status and its actor-attributed audit row cannot diverge; cancelling an assigned booking also cancels its accepted assignment rows atomically. Any rejection rolls the entire call back. These functions are executable only by `service_role`; the application server must authorize the human admin before using that credential. The database explicitly grants only the Phase A table privileges needed by the server role and authenticated RLS policies; authenticated table grants do not bypass row policies and no anon table grants are added. `0001_init.sql` and all previously applied migrations remain unchanged.

Acceptance checks: a valid admin can assign eligible helpers and produces one audit event; a non-admin actor, duplicate/oversized selection, stale or ineligible helper, or insufficient slots is rejected; a failure after an earlier candidate has been processed leaves no assignments, booking-state change, or audit event. These database checks run only against local Supabase or an explicitly disposable test project, never the linked read-only project.

## Security review follow-up: profile writes and no-show slot reuse

Authenticated clients may read their own profile and helper details, but may not directly insert, update, or delete either record. Role, approval, subscription, and vetting fields are security-sensitive; account creation, onboarding, and admin decisions write through server-only service functions after role/ownership checks. This restriction is enforced with SQL grants in a new forward-only migration, while service-role server paths remain available.

Assignment rows are historical records. A `no_show` or `cancelled` row must not consume an open booking slot; an `accepted` row does. A later eligible helper must be able to claim that slot, while the same helper cannot rejoin the same booking and completed assignments remain historical/occupied. Enforce one active assignment per booking slot with a partial unique index and apply the same active-status definition in helper claim and admin assignment functions.

Acceptance checks: authenticated host/helper attempts to change `profiles.role`, insert/update `helper_details.status`, or delete their rows are denied and values remain unchanged; a no-show slot can be claimed by a different eligible helper and assigned by an admin without deleting its historical row; concurrent claims still allow at most one active assignment for a slot. Tests run against local Supabase only. `supabase/migrations/0001_init.sql` and all previously applied migrations remain immutable.

## Stage 3.3 atomic no-show transition

The host no-show action uses one service-role-only Postgres function. It rechecks the persisted host role and booking ownership, loads `no_show_minutes`, locks the booking and target assignment, and accepts only an accepted assignment with no check-in after the configured deadline. In that transaction it records `no_show_at`, changes only the target assignment to `no_show`, increments that helper's strike once, creates a fresh offer round only for that slot, preserves every other assignment/check-in, and appends one host-attributed audit event. Repeating the request for the same already-recorded no-show returns the existing result without another strike or audit row. Invalid actor, owner, status, check-in or timing leaves every row unchanged. A replacement slot offer uses the latest slot round; initial offers continue to share the booking-wide window. Both ranking paths use `app_config.rotation_lookback_days` (initial value 30).

If another helper has already checked in, the booking remains `in_progress`; helper job reads and atomic claims may expose only its unoccupied no-show slot, and a replacement claim must not regress the booking status. Otherwise an assigned booking reopens to `open`. No-show history remains immutable in `booking_assignments`; the partial unique index permits a replacement assignment in the same slot. Existing offer expiry rules remain aligned between read and claim paths.

The 60-minute host resolution interval is stored as `app_config.no_show_recovery_minutes` (initial value 60). The owner decided that the follow-up closes only the vacant slot and never cancels other helpers' assignments. Host choices are recorded as `proceed_fewer` or `close_vacant_slot`; either decision prevents further offers/claims for that slot. “Close vacant slot” changes the booking to cancelled only when it has no remaining accepted/completed assignment; otherwise the booking and every remaining helper assignment stay active. A host may not choose `proceed_fewer` if no other helper remains assigned. The decision is host-owned, atomic, replay-safe, audited, and available only after the configured recovery interval. The host view obtains readiness from a service-only database function using the database clock. When another helper still owns an accepted slot, a no-show wrapper preserves the booking's `assigned` state so host code issuance and helper work continue; an in-progress booking stays in progress. No host payment or refund is introduced in Phase A.

Acceptance: early, wrong-host, wrong-role, checked-in and non-assigned requests are denied without partial writes; a valid no-show is atomic and replay-safe; two concurrent submissions create exactly one strike/event; all other helper assignments and check-ins remain unchanged; the slot is claimable by an eligible replacement; an in-progress booking stays in progress. Local-Supabase tests cover transaction rollback, concurrency and helper visibility/claim. Applied migrations, including `0001_init.sql`, remain immutable.

## Follow-up: claim/cancellation race, offer-window visibility, and multi-service pricing

The slot-claim database function must lock and recheck the booking row before inserting an assignment, so it serializes with admin cancellation and cannot reopen a booking after cancellation wins. The final review recheck found no remaining actionable findings. Local Supabase applied migrations through 0015 only; applied migration 0001 and all earlier migration files remain unchanged.

### Stage 2.3 session refresh seam

Audit finding: the central proxy currently refreshes/authenticates only `/admin`; `/app` and `/helper` pass through without refreshing an expired Supabase session. Its current cookie adapter updates only the outgoing response, not the request cookies consumed by the same render. Supabase's current Next.js SSR guidance requires refreshing in Proxy and updating both request and response cookies. The fix is limited to protected page GETs: call `auth.getClaims()`, feed refreshed cookie values back into the request before rendering, and preserve them on the response. Do not refresh API or Server Action POSTs in Proxy because that would run auth/session work before the shared rate-limit step; those handlers/actions can refresh through their cookie-aware Supabase client during the ordered authorization phase. This is session maintenance only, not authorization: every page, action, and API must keep its current server-side role/ownership check (`requireActor`, `requireAdmin`, or route policy). Tests cover both cookie directions, API/action bypass, public-path bypass, and fail-closed prototype gating. Official references: [Supabase SSR with Next.js](https://supabase.com/docs/guides/auth/server-side/creating-a-client?environment=client-component) and the Next.js 16 Proxy guide in `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`.

Implemented the page-GET refresh seam in `src/proxy.ts`. The proxy now passes refreshed cookies into the request render and the response; it deliberately does not refresh API POSTs ahead of rate limiting. `/admin/login` is explicitly public and no longer gets caught by the former unauthenticated admin redirect-to-self behavior. This did not weaken admin authorization: all admin pages/actions still call `requireAdmin`. Tests cover host/helper/admin page refresh, request/response cookie propagation, protected API bypass, public admin login, and prototype-off 404 behavior. The expired-token refresh is verified at the cookie adapter seam with Vitest; a real Supabase session-expiry browser test remains a separate closeout check.
