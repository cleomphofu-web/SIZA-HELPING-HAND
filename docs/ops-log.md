## 2026-10-27 — TOTP replay proof and local guard migration

- A local disposable-auth test confirmed Supabase Auth accepts the same TOTP code again on a fresh challenge during its time window. Added the private `admin_mfa_code_uses` table and service-only atomic reservation RPC in forward-only migration `20261027013000_admin_mfa_replay_guard.sql`, applied to loopback Supabase only.
- The server now HMACs the factor UUID and submitted code with the service-role key, reserves that digest before calling Supabase Auth, and fails closed if the digest was already used or the database is unavailable. The default 90-second replay window is configurable in `app_config`; raw codes are never persisted. Unit tests cover digest secrecy, fail-closed behavior, action ordering and replay denial; local integration verifies duplicate rejection and exactly one winner across 12 concurrent reservations. The test also records that direct Supabase Auth accepts replay, proving why the app guard is required.
- The factor and synthetic digest are local-only test data; test auth identity teardown deletes the identity. Digest rows expire within the configured window and are pruned on later reservations. No linked project, applied migration, `.env`, external provider, or real owner account was accessed. Fresh independent replay-guard reviews and full verification remain pending.
